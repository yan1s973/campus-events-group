# ADR 001 — Taux de remplissage pour une capacité nulle

- **Statut** : acceptée
- **Date** : 2026-10-28
- **Auteur** : Yanis (C) — commit examiné : `a91201b`
- **Fonction concernée** : `taux_remplissage(inscrits, capacite)` dans `campus.py`

## Contexte

Un événement encore vide peut être créé avec une capacité égale à 0 (incident D).
Le calcul actuel `inscrits / capacite * 100` provoque alors une division par zéro :
`taux_remplissage(0, 0)` lève `ZeroDivisionError` et le traitement s'interrompt.

Or le contrat du README indique : « Une capacité nulle avec zéro inscrit est valide :
pas d'inscription possible, zéro place, taux de 0.0. »
Il faut donc décider explicitement du résultat pour ce cas, sans masquer les vraies données invalides.

## Options étudiées

| Option | Description | Avantages | Inconvénients |
|---|---|---|---|
| 1. Lever une erreur | `ValueError` dès que la capacité vaut 0 | Simple, aucun calcul trompeur | Un événement vide mais valide devient une erreur ; contraire au contrat |
| 2. Renvoyer `None` | « pas de taux » quand la capacité vaut 0 | Distingue « pas de places » de « 0 % » | Chaque appelant doit gérer `None` ; le retour n'est plus toujours un `float` |
| 3. Renvoyer `0.0` | 0 inscrit sur 0 place = 0 % de remplissage | Conforme au contrat ; toujours un `float` ; pas de cas particulier chez l'appelant | Ne distingue pas, à lui seul, un événement sans places d'un événement vide qui a des places |

## Décision

**Option 3** : `taux_remplissage(0, 0)` renvoie `0.0`.

Les autres entrées hors du domaine restent refusées par `ValueError` :
`capacite < 0`, `inscrits < 0` ou `inscrits > capacite` (donc aussi `taux_remplissage(1, 0)`).

Raisons : c'est ce qu'impose le contrat ; le résultat reste un nombre, cohérent avec les autres
fonctions pour une capacité nulle (`peut_inscrire(0, 0)` renvoie `False`, `places_restantes(0, 0)` renvoie `0`) ;
et les données réellement invalides ne sont pas masquées.

## Conséquences

- Positives : plus d'interruption pour un événement vide de capacité 0 ; aucun traitement spécial chez l'appelant.
- Négatives : un taux de `0.0` ne suffit pas pour savoir si l'événement a des places ; il faut consulter la capacité.
- Hors périmètre : le contrôle des types (`"10"` au lieu de `10`), comme le précise le contrat.

## Test associé

La décision est vérifiée par ces cas, à couvrir dans le test de régression de l'incident D :

| Entrée | Résultat attendu |
|---|---|
| `taux_remplissage(0, 0)` | `0.0` |
| `taux_remplissage(1, 0)` | `ValueError` |
| `taux_remplissage(5, 10)` | `50.0` (cas nominal inchangé) |

Commandes de vérification : `python -m unittest discover -s tests -v` puis `python tools/verifier.py D`.
Avant la correction de l'incident D, le vérificateur D échoue ; après, il doit réussir.
